# pm 票券規範

票是**需求與驗收的紀錄**，不是實作說明書。實作方式會變，寫進票只會過期；驗收條件不會。

## 位置與命名

- 票放在 `pm/<專案名稱>/`。：
- 檔名：`[{代號}-{編號}]{標題}.md`（例如 `[NE-12]…`、`[BG-3]…`、`[ST-1]…`），標題用中文、動詞開頭、不超過 20 字
- 編號：先 `git fetch origin`，列出**該專案資料夾**內現有的票（以 origin/main 為準），取最大編號 + 1。**不重複使用、不重新編號**；開完立刻 commit 並 push，避免多個對話撞號
- 截圖：`pm/<專案>/images/{代號}-{編號}-{簡短英文說明}.png`
- 範本與下文的 `NE-n` 是舉例，BG、ST 專案的票把代號換成 `BG`、`ST`；跨專案的相依關係寫完整代號（例如 `NE-66`、`BG-2`、`ST-1`）

## 開票前

- 有不明確的地方先問使用者，不要自己假設
- 一批需求先對照 `design/` 的設計文件；設計文件沒寫到的決策，先補進設計文件或 `design/06-roadmap/open-questions.md`
- 一個需求一張票。即使兩張票會動到同一份程式碼也分開開

## 票的內容範本

```markdown
# [NE-n] 標題

> 狀態：待辦

## 內文

### 需求
這張票要解決什麼問題、玩家或開發者會得到什麼。

### 來源
誰在什麼時候提出（日期、對話或文件出處）。

### 驗收條件
- [ ] 可觀察、可驗證的條件，一條一件事

### 測試流程
1. 怎麼操作
2. 預期看到什麼

---

# 跟其他票的關係

- Blocks：無
- Blocked by：無
- Related：無

---
```

狀態：`待辦`、`進行中`、`完成`，另有兩種結束狀態：`取消`（不做了）、`封存（由 NE-n 取代）`（需求還在，但改由新票處理；舊票底下加「# 封存」段落說明原因，新票的 Related 寫回舊票）。開始做時改成 `進行中`；交付後改成 `完成`，並把驗收條件逐條打勾。

相依關係要**雙向維護**：A 票寫 `Blocks：NE-B`，B 票就要寫 `Blocked by：NE-A`。

## Commit 段落（每次交付加一段）

```markdown
# Commit-1

## 內文

原本的問題或缺少的功能是什麼。
改成什麼行為（用玩家或開發者看得到的語言描述）。
驗收了什麼、結果如何。

### 測試結果

| 項目 | 結果 |
|---|---|
| 完整測試套件 | 通過 N / N |
| 資料驗證 | 0 錯誤 |
| 執行 log | 無 ERROR |

### 截圖

![畫面說明](images/NE-n-xxx.png)
```

## 不要寫進票

- 實作細節：檔名、函式名、類別名、資料結構、演算法選擇
- 常設品質要求（`CLAUDE.md` 第一節）：那是每張票的前提，寫進去只是雜訊
- 對話語氣：「幫你…」「你可以…」「麻煩…」
- 「還沒做什麼」「待辦事項」：未完成的部分留在驗收條件的未勾選項與狀態欄
- 要提醒使用者的事（下一步建議、風險、待確認選項）：寫在對話回覆，不寫進票

## 範例

**Commit 段落（好）**

> 魚缸裡累積的泡泡和履歷只能一顆一顆點，掛機一個下午回來要點幾十下。
> 現在有「一鍵收集」按鈕和空白鍵快捷鍵，一次收完畫面上所有掉落物，收集時泡泡依序破掉、音效音高逐顆升高。
> 放置 30 分鐘後按一次收集，畫面上的掉落物全部收完，金額與履歷數量和逐顆點擊的結果一致。

**Commit 段落（不好）**

> 我幫你在 `drop_tray.gd` 加了 `collect_all()`，另外 `DropData` 多了 `pitch_step` 欄位。音效的部分還沒驗證。

## 使用者在意的事（2026-10-07；總表見 skill `user-priorities`）

- 驗收條件要**可觀察、可驗證、能證明問題真的解決**：寫出怎麼量（工具、場景、門檻）、要附什麼截圖、自動檢查擋什麼；不要寫「看起來合理」。使用者會用實機畫面檢驗，沒有重現與驗證不能結案（見 skill `visual-verification`）。
- 一張票要「確實修復相關的所有問題或實作所有功能」：開票前把使用者提到的每一個症狀都列進需求，並在驗收條件逐項對應，不要只解決最顯眼的一項。
- 結案被使用者推翻時：舊票改 `封存（由 NE-n 取代）` 並寫「# 封存」說明原因，新票的 Related 寫回舊票；不要偷偷改回進行中。
- 使用者說「只開票」就只開票（含設計文件、試作 patch 放在 `pm/<專案>/attachments/`），不要順手實作。
- 票要附 handoff 時（換 session），handoff 文件放 `pm/handoff/`，寫清楚使用者在意的事與未完成清單。
